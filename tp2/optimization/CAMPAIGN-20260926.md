# Speed, quality and capacity campaign — 2026-09-26

Goal: maximize decode and prefill without losing quality, evaluate a co-worker's
[qwen38-spark-recipes](https://github.com/original-el8/qwen38-spark-recipes) levers
and two newer checkpoints, and size the KV cache for **8 concurrent max-context
sessions** with **24 GiB pinned KV per rank** and a **118 GiB used-RAM ceiling**.

**Outcome:** the new default is `hc-adaptive+cg4+m5500h` with `kv_cache_gib: 24`.
It holds the previous speed (no lever beat the existing kernels on TP2), adds
+3–4% decode at mid concurrency, runs the newer step-5500 QAD trunk at no speed
cost, and passes an 8 × 258K concurrent-session test at 102.5 / 99.5 GiB peak.
Treat it as a capacity and freshness upgrade, not a speed jump.

Raw harness output and a generated summary of every arm:
[`results/tp2/campaign-20260926/`](../../results/tp2/campaign-20260926/summary.json).

## Method

Every arm changes one axis from `hc-adaptive` (pinned `nightly-20260923` image,
main checkpoint, BF16 SSM state, FlashInfer GDN prefill + CUDA GDN decode, MTP3
probabilistic/block, 20 GiB KV). Profiles are composable `launch.py` modifiers
(`hc-adaptive+cg4+m5500h`); the unmodified profile was verified to produce the
byte-identical Docker command of the previous launcher on both ranks.
`campaign.py` runs each arm: coordinated switch → smoke → unmodified LIL v0.6.2
(8K/32K/64K C1/C8, standalone cold prefill, C3/C5) → quality. Later checkpoint
arms used a quick screen (8K/64K prefill, 8K C1/C8, 20 s windows) plus MMLU-Pro.

Quality (`quality_eval.py`, frozen and hashed inputs): teacher-forced NLL on
wikitext-2 and CPython source (64 + 48 chunks of 1,024 tokens, prefill path);
GSM8K first 250, greedy, thinking off (decode path); MMLU-Pro 1,000 stratified
questions, direct answer. Paired comparisons use per-token deltas and exact
McNemar tests. Steps/s is reported with acceptance length: C1 tok/s ≈ steps/s ×
acceptance, and acceptance swings ±0.1 between single cells.

**Noise floor** (two runs of the identical baseline): wiki NLL Δ 0.0047 ± 0.0020,
MMLU-Pro 67.2% vs 66.9% with 71 questions flipping (p = 0.81). Differences
smaller than this are not attributable.

### Capacity: 8 concurrent max-context sessions

`kv_cache_gib: 24` gives **2,675,242 KV tokens (10.21 × 262,144)**, versus
2,229,941 (8.51×) at 20 GiB; FP32 SSM state would give ~2.50M at 24 GiB.
`capacity_check.py` (both ranks' RAM watched, 118 GiB limit):

- Phase 1: eight unique 258,000-token prompts with passkeys at 5/50/95% depth:
  24/24 retrieved, 0 preemptions, 913 s (vLLM admits one long prefill at a time).
- Phase 2: a new question on all eight cached contexts at once: **8/8 decoding
  concurrently**, prefix-cache hit rate 95.3%, peak KV 74.3%, 8/8 retrieved while
  generating 417–512 tokens, 0 preemptions, 74–80 s per session.
- Peak used RAM **102.5 GiB (r0) / 99.5 GiB (r1)**.

## Checkpoint findings

- `qad-step-4000` (`629bc321`) is **byte-identical** to `main` (`7c4f1bc1`) in all
  48 weight/tokenizer files; only README and the config's architecture alias differ.
- `qad-step5500-ple1000` (`60215d26`) has 5,500 trunk steps plus PLE refinement,
  but stores attention in **BF16** and MTP routed experts as **MXFP8** PTQ. b12x has
  no MXFP8 MoE kernel (`moe_backend='b12x' is not supported for MXFP8 MoE`); the
  drafter inherits the target backend. Triton has no SM121 MXFP8 kernel; Marlin
  works but costs 14% of C1 steps together with the BF16 attention reads.
- Both model cards state attention and MTP were never distilled. Verified: main's
  MXFP8 attention dequantizes to step-5500's BF16 at 2.65% ± 0.03% relative error
  (MXFP8 rounding; the same source weights), and all 29 MTP non-expert tensors are
  byte-identical. `build_hybrid.py` therefore keeps every trained step-5500 tensor
  and restores main's MXFP8 attention and W4A16 NVFP4 MTP experts (3,312 tensors
  dropped, 5,088 added, 5 shards rewritten, the rest hardlinked). Both ranks built
  byte-identical trees ([manifest](../manifests/model-5500h.sha256)). The MTP head
  affects only draft acceptance, never target outputs.
- Published as [JMNI-Labs/Qwen3.8-Flash-Next-NVFP4-QAD5500-Hybrid](https://huggingface.co/JMNI-Labs/Qwen3.8-Flash-Next-NVFP4-QAD5500-Hybrid)
  (revision `87c8f2fb`, model card in [`tp2/hf/MODEL_CARD.md`](../hf/MODEL_CARD.md)). All 58
  files except the card were verified against the manifest on Hugging Face after upload.

## Nondeterminism (open issue)

Scoring the same token chunk repeatedly on an idle server changes per-token
log-probabilities by 0.16–0.29 nats on average (up to 9 nats); greedy decodes
diverge after 10–44 tokens. It is identical in every arm, including the stock
`baseline` profile without HC overrides, so it is an upstream vLLM/b12x property.
`B12X_DYNAMIC_DETERMINISTIC_OUTPUT=1` cannot start on this build: the tuned MoE plan
records direct routing, which lacks a deterministic variant, and a grouped fallback
needs an unplanned `moe.w4a16.topk_sum` program. The source is not confirmed.
This limits how precisely quality differences can be measured.

## Co-worker recipe review

Their TP2 recipe measures below this one (8K prefill 3,350 vs 3,739) because their
stack cannot shard HC at TP2. Their levers here: drafter b12x backends are already
inherited in this vLLM; block-size 32 is moot (mamba page forces 1,472-token
attention blocks); `index_share_for_mtp_iteration` is already false; newer b12x is a
TP4 decode gain but a TP2 regression (above). The one useful idea was setting the
drafter's own MoE backend, which is what makes the published step-5500 runnable.

## Fixes made along the way

- `config.find_ipv4_gid` crashed on unpopulated RoCE GID slots (EINVAL), so a fresh
  install of the packaged repo could not start; the live ranks used an older launcher.
- `download_model.py` failed under Xet with a read-only HF cache; it now keeps
  `HF_HOME` inside the snapshot's ignored `.cache`.
- `select_profile.py` deleted failed candidate containers without their logs; it now
  saves `evidence/<stamp>-failed-<profile>-rank<N>.log` first.
- `campaign.py` restore waits for a rollback start before switching back.
